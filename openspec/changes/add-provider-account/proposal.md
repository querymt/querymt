# Proposal: Provider account snapshots (plan, usage windows, credits)

## Why

A user running Codex, xAI or Anthropic through an OAuth subscription cannot see how much of their allowance is left. Each of those services exposes it (a weekly window for Codex, a weekly credit pool for Grok, a five-hour and a seven-day window for Claude) but through unrelated endpoints, headers and shapes, and QueryMT has no place to ask. API-key providers vary: most expose nothing to an inference key (OpenAI, Anthropic, xAI, Mistral, Groq and Google keep usage behind admin or management keys), while some expose a balance (DeepSeek `GET /user/balance`, Moonshot `GET /v1/users/me/balance`) or even spend budgets with reset windows (OpenRouter `GET /api/v1/key`). The contract therefore has to let a provider decline per credential, not per provider kind.

QueryMT needs one small contract that lets a provider plugin answer "what does this provider know about the credential it is running under", lets the host answer "nothing" for providers and credentials that have no such concept, and exposes the result to ACP clients without making them aware of each provider's API.

## What Changes

- **New concept: provider account snapshot.** A snapshot is what a provider reports for the credential in the resolved configuration: an optional plan name, zero or more usage limits (each a percentage used, with optional window length, reset time and scope), and an optional credit balance. Usage is one part of the snapshot, not the whole concept, so the contract is named *account*, not *usage*, and the same shape serves subscription windows (Codex, Claude, Grok), prepaid balances and "nothing to report".
- **Plugin contract (additive, optional).** HTTP provider factories gain a request/parse pair mirroring model listing: build one HTTP request for the account snapshot from the resolved config, or decline (`None`) when the provider or that credential type has no account data; then parse the response into the snapshot. The generic factory trait gains an async `account` operation returning an `AccountReport` enum (`Unsupported` or `Account(snapshot)`) with a default of `Unsupported`. The Extism plugin macro exports the pair as optional functions; the host treats a plugin without the exports as `Unsupported`. Plugins that do not implement the contract need no change and keep working.
- **Three plugins implement it:** `codex` (ChatGPT usage endpoint, always, since Codex is OAuth-only), `xai` (Grok credits endpoint when the credential is an xAI OAuth token; declines for API keys) and `anthropic` (Claude OAuth usage endpoint when the credential is an OAuth token; declines for API keys).
- **Wasm account requests go only to allowed or declared hosts.** The host issues an account request for a Wasm plugin only when its host is one of the allowed hosts the plugin was loaded with or an account host the plugin declares. A plugin declares account hosts through one optional static export, read once at load and used for account requests only; it does not widen what the plugin itself may reach. Codex and Anthropic declare nothing, because their usage endpoints are on the base-URL host. xAI declares `cli-chat-proxy.grok.com`, so its account query works with no configuration, and that host is contacted only for an xAI OAuth token.
- **New ACP method `querymt/auth/account`.** Params `{ provider?: string, refresh?: bool }`. Returns one entry per configured provider (or the one requested) with a status of `ok` (with the snapshot and its fetch time), `unsupported` (no snapshot for this provider/credential), `unauthenticated` (no usable credential), or `error` (with a message). Credentials are resolved exactly as for model listing (OAuth refresh, stored key, environment). Successful and unsupported answers are cached for 60 seconds per provider; `refresh: true` bypasses the cache; auth mutations invalidate it. The method is advertised in `querymt/capabilities` under `methods` and as feature `auth_account`. The change is pull-only: a client that wants a fresh value after a turn calls the method with `refresh: true`.
- **qmacp and qmcp.** One flat qmacp command `qmacp account [--provider] [--refresh]` (shaped like `models`, gated on the `auth_account` capability) and one read-only qmcp MCP tool `account` with the same arguments returning the payload under `result`. No new subcommand group.

## Non-goals

- Live updates: reading usage from chat response headers (`x-codex-*`, `anthropic-ratelimit-unified-*`), merging them into the cached snapshot, a `querymt/auth/accountChanged` notification and its qmacp/qmcp stream event. Split into a follow-up change after review: it carries the only breaking Rust API change (response headers on the streaming outbound result) and open questions about partial snapshots, freshness and debouncing that the pull path does not have. Anthropic API-key per-minute rate-limit headers are not subscription usage and stay out of both changes.
- Applying the allowed-hosts check to model listing and prepared chat requests. The host runs those for Wasm plugins without the check today; this change adds the check for account requests only and leaves the existing paths as they are.
- Multi-request snapshots (for example fetching a plan name from a second profile endpoint). Each plugin issues one request; a plan name that needs another call stays `None`.
- A `qmt` CLI command (qmacp is covered; the main CLI is not), a `/usage` slash command, dashboard or desktop rendering, background polling, "approaching limit" notifications, and persisting snapshots.
- Account snapshots for mesh peers' providers, for `kimi-code` and for local providers. The contract allows them; no plugin implements them here.
- OpenRouter, DeepSeek and Moonshot API-key snapshots. Explored and confirmed to fit the snapshot shape without change (OpenRouter budgets and free-model daily quota as `limits`, key `limit_remaining` as `credits`; DeepSeek and Moonshot as `credits` only). Each is a request/parse pair in its own provider crate with no host, runtime or ACP work, so they are a short follow-up change once this one lands.
- Any change to cost accounting (`llm-cost-accounting`); a snapshot is provider-reported, not derived from QueryMT's own token accounting.

## Capabilities

### New Capabilities

- `provider-account-snapshot`: the snapshot data model, the factory request/parse contract, the Extism exports, the allowed-hosts check, parser tolerance and the three plugin implementations.
- `provider-account-acp`: the `querymt/auth/account` method, credential resolution, status mapping, caching and capability advertisement.
- `qmacp-account`: the `qmacp account` command and the qmcp `account` tool.

### Modified Capabilities

None. No existing spec's requirements change; `provider-resolution`, `agent-configuration` and `llm-cost-accounting` are untouched.

## Impact

- `querymt` (no feature gate for the types; `http-client` for the adapter, `extism_host` for the host side, `extism_plugin` via the macro crate): new public types `AccountReport`, `ProviderAccount`, `UsageLimit`, `CreditBalance`; new default methods `LLMProviderFactory::account`, `HTTPLLMProviderFactory::account_request`, `parse_account` and `account_hosts`; new Extism wire structs; `humantime` requirement raised from `"2"` to `"2.3"`. All trait additions have defaults, so existing implementors compile unchanged, and no existing public item changes shape. The Extism contract gains three optional exports detected by name, like `list_models_static`; no contract version bump is needed because hosts and plugins without the exports interoperate. Flagging for review: if the reviewer prefers an explicit version signal, `ITEM_AWARE_CHAT_CONTRACT_VERSION` is the wrong knob and a dedicated `ACCOUNT_CONTRACT_VERSION` export would be the alternative.
- `querymt-extism-macros`: `impl_extism_http_plugin!` exports `account_request`, `parse_account_response` and `account_hosts`.
- `qmt-codex`, `qmt-xai`, `qmt-anthropic` (`extism` and `native` features; wasm32-wasip1 builds): factory implementations and parsers.
- `querymt-agent-runtime` (`oauth` for OAuth credentials, no new feature): new ACP method, cache, capability entry. **Wire shape added**: `querymt/auth/account` response and the `auth_account` capability flag. No config keys, no DB schema change, no hook or middleware change.
- `qmacp`: one `Command` variant and one `pub` gate+call helper. `qmcp`: one `Command` variant (tool schema derived), one `read_only` entry. READMEs and skill docs. No change to existing commands, tools or event shapes.
- `querymt-agent`: facade re-exports only. `querymt-agent-py`, `querymt-mobile-ffi`: no change (ACP-level feature).
- Native plugin ABI: `stabilize-native-plugin-abi` has not landed, so the added trait methods change the `dyn LLMProviderFactory` and `dyn HTTPLLMProviderFactory` vtables and this change bumps `NATIVE_PLUGIN_API` to 3 (native plugins must be rebuilt; Wasm plugins are unaffected). That open change also plans its ABI as version 3 and must move to 4 if this lands first.
- Typeshare: `ProviderAccount`, `UsageLimit` and `CreditBalance` are typeshared behind `querymt`'s `type-generation` feature; the runtime's `ProviderAccountStatus` is typeshared. `querymt-desktop` follow-up: render per-provider plan, limit bars with reset times and credits on the provider/auth settings view, using `querymt/auth/account`, and re-pull with `refresh: true` when a turn ends.
- `CHANGELOG.md` Unreleased: "Added" entries for the plugin contract and the ACP method plus a "Breaking" entry for the native ABI bump.

## Risks

- **Undocumented endpoints.** `chatgpt.com/backend-api/wham/usage`, `cli-chat-proxy.grok.com/v1/billing` and `api.anthropic.com/api/oauth/usage` are what the vendors' own CLIs call, not published APIs. They can change shape or disappear without notice. A failure is contained to that provider's entry (`error`) and never affects chat or other providers; parsers treat every mapped field as optional, so a dropped field removes one plan, limit or credit instead of the whole snapshot; the gated live checks (task 3.5) detect drift.
- **Client identity and vendor terms.** The requests identify as the vendor's CLI. For Codex and Anthropic this is the identity the existing OAuth chat path already presents on the same host (`originator: codex_cli_rs`; `anthropic-beta: oauth-2025-04-20` with a `claude-cli` user agent). For xAI it is new: the provider talks only to `api.x.ai` today and sends no CLI token header, and this change adds `cli-chat-proxy.grok.com` with `X-XAI-Token-Auth: xai-grok-cli`. Whether a vendor's terms permit this use of a subscription credential is a maintainer decision this proposal does not settle. The xAI request keeps the CLI token header and user-id header for now; one probe showed the endpoint answers with the bearer token alone, so the code carries a `TODO` to identify as QueryMT or drop them. The xAI implementation can be dropped on its own, which leaves xAI `Unsupported` and changes nothing else.
- **Plugin-declared account hosts.** A plugin names its own account hosts, so the check does not protect against a plugin that is itself malicious. That is the trust the host already gives the plugin's `base_url` export, whose host is allowed without configuration. What the check does stop is an account request to a host that was neither configured nor declared at load. Requiring the user to list the host in `allowed_hosts` instead was rejected: it makes a first-party OAuth provider fail until the user edits config, for no gain over the existing `base_url` trust.
